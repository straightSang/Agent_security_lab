RFC-001 · 선택지 B 승인 · 실행 완료 · 2026-09-03

공개 인터페이스 정리

make_runtime_result이 필요한지 묻는 질문에서 출발했다. 감사해 보니 이 함수 하나의 문제가 아니었다. agent.py가 공개한 이름 14개 중 12개를 아무도 쓰지 않는다.

대상 AI_Agent_Security_Lab_v2 영향 agent.py · runtime.py 상태 C1~C8 실행 완료 · 회귀 7스위트 PASS

그렇다. make_runtime_result은 필요 없다. 호출처가 0이다.

다만 그것만 지우는 건 증상 처리다. 주석은 “Day 1~8 코드와 문서가 이 형태를 참조하므로 남겨 둔다”고 말하는데, Day 1~8 코드는 이 저장소에 없다. 단일 트리로 옮기면서 AI_security_Lab에 그대로 남겨 뒀다.

즉 호환 어댑터가 가리키는 대상이 존재하지 않는다. 어댑터가 아니라 죽은 채로 공개된 표면이다.

실행 완료. 선택지 B(C1~C8) 승인 후 적용했다. agent.__all__이 14개에서 3개로 줄었고, 실행 경계와 보안 판정 코드는 한 줄도 바뀌지 않았다. 기존 회귀 6스위트가 그대로 통과한 것이 그 근거다.

1

감사 결과

ast로 src/와 tests/ 전체의 from … import 문을 파싱해, 각 이름을 실제로 누가 가져다 쓰는지 집계했다. 문자열 검색이 아니라 구문 트리 기준이므로 부분 일치로 인한 과다 집계가 없다.

가장 분명한 사례

make_runtime_result은 runtime.py가 정의하고 → agent.py가 import하고 → __all__로 재수출한다. 그리고 아무도 호출하지 않는다. 정의부터 재수출까지 전 구간이 죽어 있다.

2

왜 정리가 필요한가

일반적인 프로젝트라면 “안 쓰는 export가 좀 있네” 정도다. 이 저장소에서는 다르다. README와 위협 모델이 반복해서 주장하는 명제가 하나 있기 때문이다.

“도구가 실행되는 지점은 _dispatch() 하나뿐이며, 거기 도달하려면 여섯 관문을 순서대로 통과해야 한다.”

이 주장을 검증하려는 사람은 공개된 진입점을 전부 확인해야 한다. 지금은 그게 14개다. 실제 인터페이스는 2개인데 감사 비용은 14개어치다.

세 가지가 구체적으로 나빠진다.

  • 감사 비용. 외부인이 “이 중 무엇이 Runtime을 우회할 수 있나”를 14번 확인해야 한다.
  • 주장의 선명도. 진입점이 많아 보이면 “경계가 하나”라는 문장의 설득력이 떨어진다. 논문 심사에서 먼저 지적될 지점이다.
  • 재발 위험. 죽은 표면이 남아 있으면 나중에 누군가 그걸 “있으니까” 쓴다. ARGUMENT_SPEC이 정확히 그렇게 두 번째 인터페이스 목록이 되었다.

제안 구조

원칙 하나로 정리된다. 공개 인터페이스는 실제로 쓰이는 것과 앞으로 쓸 것만 담는다. 내부 구현은 이름 앞에 밑줄을 붙이거나 __all__에서 뺀다.

C8이 실제로 하는 검사

__all__의 각 이름에 대해, 저장소 안에서 실제로 import되는지를 ast로 확인한다. 아직 안 쓰이는 것은 PLANNED 목록에 사유와 함께 등록해야 통과한다. 지금은 run_agent_loop 하나가 여기 들어간다 — W1 D4 model-in-the-loop 실험에서 사용 예정.

이 방식이면 “나중에 쓸 거라서 남겨 둔다”가 주석 속 구전이 아니라 깨질 수 있는 선언이 된다. W1 D4가 끝나면 PLANNED에서 자동으로 빠져야 하고, 안 빠지면 테스트가 알려준다.

실행 중 확인한 것 — READ_ONLY_TOOLS의 정체

“agent.READ_ONLY_TOOLS는 MCP schema 검사에 쓰이는 것 아닌가”라는 확인 요청이 있었다. 실행 전에 검증했고, 다른 물건이었다.

이름타입쓰임
security.tool_schema.
READ_ONLY_PROFILE		ToolProfile검사에 쓰인다. validate_tool_schema()의 첫 인자
agent.READ_ONLY_TOOLSlist[dict]모델에게 광고할 도구 정의 목록. 검사와 무관

후자를 검사 함수에 넣으면 AttributeError: 'list' object has no attribute 'exposed_tools'가 난다. 이름이 비슷해 혼동을 부르고 있었으므로, 삭제로 그 위험까지 함께 사라졌다.

연구 관점에서 한 가지 덧붙인다. 이 정리는 코드 위생 문제가 아니라 “감사 가능한 공격 표면을 최소로 유지한다”는 이 랩의 원칙을 저장소 자신에게 적용하는 일이다. 논문 부록에 “공개 진입점 3개, 그것을 회귀로 고정” 한 줄을 쓸 수 있는지 여부가 걸려 있다.
